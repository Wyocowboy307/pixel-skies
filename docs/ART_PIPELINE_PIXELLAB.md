# Production Art Pipeline — PixelLab

Production art is generated through PixelLab, reviewed, and imported by an
explicit approval step. Nothing is generated ad hoc inside feature work.

## Two trees, kept apart

```
assets/art/production/    PixelLab-generated, reviewed, approved
assets/art/placeholder/   generated by tools/build_pixel_assets.py
```

`scripts/data/asset_paths.gd` resolves a logical path — for example
`aircraft/trailhopper_4/trailhopper_4_side.png` — to the production file when
one exists and the placeholder otherwise. **Approving an asset is dropping it
into the production tree.** No code changes, no path edits, and the game keeps
running throughout the migration. Nothing in the engine may reference either
tree directly.

## The loop

```
tools/.venv/bin/python -m artgen.cli status              # what is approved, what is not
tools/.venv/bin/python -m artgen.cli generate <key>      # candidate -> .art_candidates/
tools/.venv/bin/python -m artgen.cli review              # mechanical style gate
tools/.venv/bin/python -m artgen.cli approve <key>       # snap to palette -> production/
tools/.venv/bin/python -m artgen.cli reject <key>        # discard the candidate
./verify.sh shots plane_gate                             # judge it in the running game
```

Run from `tools/`. The API key is read from `PIXELLAB_API_KEY` or
`~/.pixellab_key` — never from a command line or a prompt.

## The specification is the contract

`tools/artgen/spec.py` holds every asset: its prompt, exact canvas, camera view,
direction and destination. The shared `STYLE` and `NEGATIVE` clauses are appended
to every prompt, which is what stops each new asset drifting into its own
direction. **If `STYLE` or `NEGATIVE` changes, the whole set is regenerated** —
not just the next asset.

Structured controls are pinned to match `PIXEL_STYLE_GUIDE.md`:
`outline='single color black outline'`, `shading='flat shading'`,
`detail='low detail'`, `no_background=True`.

## Style locking

The first approved asset is the **reference** (currently the Trailhopper side
view). Every later generation passes it as `style_image` to
`generate-image-bitforge`, so the set is anchored to one look rather than to a
prompt that happens to be worded similarly.

## The rejection gate

`tools/artgen/review.py` is calibrated to reject only what approval cannot
repair:

| finding | verdict | why |
| --- | --- | --- |
| wrong canvas size | reject | the spec is the contract |
| empty, or fills <10% of canvas | reject | badly framed |
| >140 distinct colours | reject | photographic, not pixel art |
| >60% of colours far off-palette | reject | a different palette, not this game |
| 36–140 colours | warn | approval snaps these to the palette |
| soft alpha edges | warn | approval hardens these |

Approval snaps every opaque pixel to the nearest locked palette entry and forces
binary alpha, so a shipped asset obeys the style guide exactly even though the
generator only came close. The first approved Trailhopper went from 70 colours
to 28, with zero soft-alpha pixels and zero off-palette colours.

**Charm is not checkable.** The gate catches only objective failures. Every
candidate must still be looked at in the running game at real size, and rejected
if it is lifeless, inconsistent with the top-down view, or too technical.

## Anchors

The plane screen draws passengers into windows and crates into a hold, so an
aircraft side sprite needs to say where those are. Pipeline-drawn art emits the
positions directly; generated art has them recovered by `tools/artgen/anchors.py`,
which finds glazing as connected components arranged in a row. A test asserts
every sprite agrees with its own anchors and that no anchor falls outside the
image — without it, passengers are drawn outside the aircraft.

## Current service status (2026-08-26)

- `generate-image-bitforge` (style-locked generation) is returning **HTTP 500**
  server-side on every call, including minimal requests. Style-locking against
  the approved reference is therefore unavailable.
- Unlocked `generate-image-pixflux` was probed twice for the airport prop kit:
  both terminals came back **isometric** despite explicit flat-top-down prompts
  and hardened negatives, which clashes with the flat-lay airport direction.
- Decision: the prop/icon kit is **on hold until bitforge recovers**, rather
  than approving assets that visibly drift. The aircraft cutaway direction is
  locked in the spec and currently shipped from the deterministic pipeline;
  two pixflux cutaway candidates were rejected (no interior / wrong facing).

## Known gaps

- Generated aircraft have no visible cargo hold, so cargo anchors are placed
  along the belly as a fallback. A future prompt should ask for an open bay.
- The installed SDK pins `usage` to a USD figure; an account on a generations
  quota returns a different shape and the strict model rejects an otherwise
  good response. `tools/artgen/client.py` therefore posts directly and parses
  the response itself.
